1. Executive Summary

The project is functionally healthy and well tested: 232 unit tests and 172 Playwright E2E tests pass, the linter reports 0 errors, and the production build succeeds. Domain logic (parsers, matchers, hypergeometric deck math, playmat reducer) is genuinely well factored and covered.

The problems are not in feature correctness — they are in the delivery and trust boundaries. Three issues stand out and should be treated as release blockers for any public deployment:

  • Digital Playmat rooms are completely unauthenticated in Firestore rules (allow read, write: if true).
  • The service worker precaches 436 MB across 9,258 entries because card images land in dist/.
  • The main JS chunk is 13.2 MB with zero code-splitting anywhere in the app.

3. Critical Findings

CRITICAL F1 — Playmat rooms have no access control

// firestore.rules
match /playmat_rooms/{roomCode} {
  allow read, write: if true;
}

Why it matters: every other collection in this ruleset was carefully scoped (the file's own header comment celebrates replacing a catch-all), but the playmat path reintroduces exactly that hole. Any unauthenticated person on the internet can read, overwrite, or delete any live match state. Room codes are short and enumerable, so the attack does not even require the link.

The room pin exists in createInitialRoomState (src/services/playmatSyncService.ts:36) but is only ever checked client-side — it is stored in the same document the attacker can read.

Recommended fix: require request.auth != null for writes at minimum; better, store hostUid plus a hashed PIN on create and gate update/delete on the room's participant list. Add a createdAt-based TTL rule or a scheduled cleanup so abandoned rooms are not permanently writable. Validate that a write only touches the writer's own side (p1/p2).

CRITICAL F2 — The service worker precaches 436 MB

PWA v1.3.0 — precache 9258 entries (436740.54 KiB)
dist/card-images       440M
dist/card-images-hd    1.8G
dist/sw.js             1.0M

Why it matters: globPatterns: ['**/*.{js,css,html,ico,png,svg,webp,json}'] in vite.config.ts sweeps public/card-images/ and public/card-images-hd/ into the precache manifest. On first load the SW attempts to download ~436 MB before it can activate. On mobile this exhausts the browser's storage quota, fails install, burns the user's data plan, and produces a 1 MB sw.js (Babel already warns it exceeds 500 KB). This directly contradicts the "PWA Excellence" goal in the project guidelines.

Note the app already has a correct CacheFirst runtime rule for the R2 image CDN — so precaching local copies is redundant work on top of being harmful.

Recommended fix: add globIgnores: ['card-images/**', 'card-images-hd/**', 'set-boosters/**', 'data/**'] to the workbox block, and lower maximumFileSizeToCacheInBytes back toward the 2–5 MB range. Target a precache under 10 MB. Serve card images exclusively through the existing R2 runtime cache.

CRITICAL F3 — 13.2 MB main chunk, zero code-splitting

13,161,516  dist/assets/index-*.js
 7,969,904  dist/assets/pokemonCardsEn-*.js
 6,580,101  dist/assets/market_prices-*.js
   424,114  dist/assets/xlsx-*.js
   295,150  dist/assets/index-*.css

grep -rn "lazy(|Suspense" src  →  no matches

Why it matters: src/App.tsx statically imports every top-level view — GameBoard, CollectionTracker, DeckManager, AdminPage, CardMappingPage, SharedCollectionViewer, PlaymatHub. A visitor opening a public share link therefore downloads the admin panel, the mapping studio, the OCR scanner (tesseract.js), the spreadsheet parser (xlsx), and the whole playmat engine. There is not a single React.lazy in the codebase.

The two multi-megabyte JSON payloads (pokemonCardsEn.json at 336k lines, market_prices.json at 320k lines) are compiled into JS chunks rather than fetched on demand.

Recommended fix: (1) wrap the six routed views in React.lazy + Suspense — this is the single highest-leverage change in the repo; (2) lazy-import tesseract.js and xlsx at the point of use, not at module scope; (3) move the large JSON datasets to public/data/ and fetch() them, so they are cacheable and versionable independently of the bundle.

4. High-Severity Findings

HIGH F4 — Admin passkey hardcoded in the client

// src/utils/adminAuth.ts
export function verifyAdminPasskey(passkey: string): boolean {
  const envPasskey = (import.meta.env.VITE_ADMIN_PASSKEY as string | undefined)?.trim();
  const defaultKey = 'poke911admin';        // ← ships in the bundle
  if (envPasskey) return passkey.trim() === envPasskey;
  return passkey.trim() === defaultKey;
}

Why it matters: the fallback string is a literal in the shipped JS, findable with one search of the bundle. Note that VITE_ variables are also inlined at build time, so setting VITE_ADMIN_PASSKEY does not fix this — it just replaces one public string with another. Client-side passkey verification is decorative by construction.

Mitigating factor (for the record): Firestore rules gate real admin data on request.auth.token.email, so the passkey unlocks the admin UI rather than the data. Any admin-only behaviour that is enforced purely in the client is nonetheless exposed.

Recommended fix: delete the passkey path entirely and rely on the Google email allowlist, or move admin identity to a Firebase custom claim (request.auth.token.admin == true) verified server-side. An allowlist compiled into the client is acceptable for UI hints only.

HIGH F5 — Any signed-in user can rewrite shared market data

match /market_prices/{cardId}      { allow read: if true; allow write: if isSignedIn(); }
match /community_stats/{docId}     { allow read: if true; allow write: if isSignedIn(); }
match /community_card_suggestions/ { allow read: if true; allow write: if isSignedIn(); }
match /community_card_pairings/    { allow read: if true; allow write: if isSignedIn(); }

Why it matters: a single account (Google sign-up is free) can overwrite or delete the price of every card that every user sees, or poison the community pairing data that setCloudApprovedMappings feeds straight into the Thai↔English matcher at app boot (src/App.tsx:19). The in-code comment already flags this as a known gap — it deserves a fix, not a note.

Recommended fix: make these collections read-only from the client. Route price updates and pairing approval through the admin path (isAdmin()) or a Cloud Function. If community submissions must stay open, split them: users write to a *_pending collection with per-document ownerUid and field-shape validation, and only an admin promotes to the canonical collection.

HIGH F6 — viewCount rule is unauthenticated and unbounded

allow update: if request.resource.data.diff(resource.data)
                .affectedKeys().hasOnly(['viewCount']);

Why it matters: there is no isSignedIn() guard and no value constraint, so any anonymous client can set viewCount to any number — including negative, a string, or a value that breaks the viewer's rendering. Because Firestore ORs allow rules, this sits beside the owner rules and widens them.

Recommended fix: constrain the value — request.resource.data.viewCount == resource.data.viewCount + 1 && request.resource.data.viewCount is int — or move counting to a Cloud Function / analytics event and drop the client write entirely.

HIGH F7 — 62 swallowed exceptions hide sync failures

Unused catch bindings by file: collectionStore.ts ×17, deckStore.ts ×6, communityStore.ts ×3, HPPresetPicker.tsx ×3, plus the scripts/ tree.

Why it matters: these sit on the cloud-sync paths. When syncProfileToCloud or loadUserFromCloud fails — permissions, quota, offline — the error is discarded and the app carries on as if the write succeeded. The store has a SyncStatus type including 'error', so the UI is ready to show this; the catch blocks simply never set it. Silent data-loss on a collection tracker is the worst possible failure mode for this product.

Recommended fix: in every cloud-write catch, set syncStatus: 'error', keep the message for a retry affordance, and log through a single reporting helper. The existing E2E suite already exercises these flows and would catch regressions. The cloudLoadedUid write guard shows the right instinct — extend it to failure reporting.

5. Medium & Low Findings

MEDIUM F8 — Stale-closure risk in the realtime playmat effects

PlaymatDuelBoard.tsx:143   missing dep 'roomState'
PlaymatDuelBoard.tsx:180   missing dep 'roomState.matchId'
PlaymatMobileController.tsx:279  missing dep 'roomState.matchId'
PlaymatMobileController.tsx:355  missing dep 'roomState'

Of the 18 exhaustive-deps warnings, these four are the dangerous ones: they are on effects that own the Firestore subscription and match lifecycle. A stale roomState captured in a subscription callback produces exactly the intermittent "board didn't update / wrong match" bugs that are hardest to reproduce. The remaining 14 are ordinary mount-once effects and can be silenced with a justifying comment.

Recommended fix: hold the live state in a ref for callback reads, or split the effect so the subscription depends only on roomCode and the handler reads through useRef. Add an E2E spec covering rematch (matchId increment) while both clients are connected.

MEDIUM F9 — useMemo calls that never memoize

CardCollectionModal.tsx:166,340  depends on `variants` — new identity every render
DeckEditor.tsx:65 · DeckViewModal.tsx:39 · CardSwapModal.tsx:48 · MissingCardsModal.tsx:29
                                 depend on `userCollectionCards` — same problem

The dependency array changes identity on every render, so the memo recomputes every time — pure overhead plus the illusion of caching. These recomputations run over the user's full collection inside modal render paths, which is precisely where mobile jank shows up.

Recommended fix: derive userCollectionCards and variants from the Zustand store with a stable selector (or memoize them one level up) rather than rebuilding the array inline in each consumer. One shared selector would fix all five sites at once.

MEDIUM F10 — Substring routing is too permissive

// src/App.tsx — getModeFromURL()
if (path.includes('/admin') || hash.includes('admin') ||
    modeParam === 'admin' || rawSearch.includes('admin')) return 'admin';

rawSearch.includes('admin') matches any query string containing the substring — ?ref=badminton, ?utm_campaign=admin-newsletter, a share link with those characters. The same pattern repeats for deck, playmat, mapping, battle. It is a correctness and UX bug rather than a breach (the auth gate still holds), but it makes routing unpredictable and hard to test.

Recommended fix: match on modeParam exact equality and on path segments (path.split('/')), and drop the rawSearch.includes branches. Consider adopting a real router — the hand-rolled logic here is already ~70 lines.

MEDIUM F11 — God files

2838  PlaymatMobileController.tsx      1287  DeckEditor.tsx
2522  PlaymatDuelBoard.tsx             1214  PlaymatHostBoard.tsx
1448  collectionStore.ts               1043  CardCollectionModal.tsx

The playmat trio alone is ~6,500 lines of component code, and the two boards duplicate substantial board-rendering and QR/share logic. collectionStore.ts mixes profile CRUD, filters, import parsing, and four distinct cloud-sync strategies (load, sync, upload, reconcile, forceSync) in one store.

Recommended fix: extract the shared board rendering into components/playmat/board/ primitives, and split collectionStore into a state slice plus a collectionCloudSync service. The pure-reducer style already used in playmatSyncService.applyPlaymatAction is the right model — it is testable and already has 540 lines of tests behind it.

MEDIUM F12 — 227 any escapes

TypeScript 6 with tsc -b in the build is being undercut by 227 any / as any sites. Firebase error handling (catch (error: any) in firebase.ts:47) is a common one and is now unnecessary — unknown plus a narrow helper is both safer and shorter.

Recommended fix: enable useUnknownInCatchVariables, add a isFirebaseError(e) type guard, and burn down any starting with the store and service layers where the payload shapes are already declared in src/types/.

LOW F13 — Dynamic imports defeated by static ones

[INEFFECTIVE_DYNAMIC_IMPORT] src/store/collectionStore.ts is dynamically imported by
  sharedCollectionService.ts but also statically imported by 6+ components
[INEFFECTIVE_DYNAMIC_IMPORT] src/data/thaiEnglishCardMap.json is dynamically imported by
  pricingStore.ts but also statically imported by MissingPricePanel, deckMapAssist,
  thaiEnglishCardMatcher

Someone deliberately wrote await import(...) to split these out, and a static import elsewhere silently cancels the benefit. The 178k-line thaiEnglishCardMap.json is the payload at stake.

Recommended fix: make the map accessible only through an async accessor in thaiEnglishCardMatcher so no module can statically import the JSON, then keep the dynamic import in pricingStore.

LOW F14 — Duplicate key in the translation generator

scripts/generate-translations.mjs:264  no-dupe-keys: Duplicate key 'prime catcher'

The second definition silently wins and the first is dropped — a data-correctness bug in generated translations, not just style noise. It is the only no-dupe-keys hit in the repo, so it is almost certainly an unintentional paste.

Recommended fix: reconcile the two entries by hand and promote no-dupe-keys to error in the oxlint config so this cannot recur.

LOW F15 — Production hygiene

  • 93 console.* calls reach the production bundle; several log Firestore errors and user state. Strip with esbuild.drop / build.minify options, or route through a level-aware logger.
  • 25 no-useless-escape warnings in cardOcrMatcher.ts, rarity.ts, ptcglDeckParser.ts, voiceCardParser.ts. Harmless today, but they signal regexes assembled by trial and error — worth a review pass given how much parsing accuracy this app depends on.
  • dangerouslySetInnerHTML at PlaymatHostBoard.tsx:1056 and PlaymatDuelBoard.tsx:2297 injects generateQrSvg() output. The generator interpolates a URL into an SVG template (qrCode.ts:331) without escaping. Currently safe because the URL is app-constructed, but a user-controlled room code or player name reaching that URL would become SVG/XML injection. Escape & < > " in the interpolated values.

6. What Is Genuinely Good

  • STRONG Test culture. 31 unit test files / 232 tests and 22 E2E specs / 172 tests, including a dedicated collectionStore.cloudGuard.test.ts and a 540-line playmatSyncService.test.ts. The pure-reducer design of applyPlaymatAction is what makes that possible — it is the best-architected part of the codebase.
  • STRONG The cloudLoadedUid guard. The comment in collectionStore.ts:22-29 explains a real, subtle boot-window data-loss bug and the guard that prevents it. This is exactly the standard the rest of the sync code should meet.
  • STRONG Secret hygiene in .gitignore. Service-account patterns, *-adminsdk-*.json, *.secret.*, and env files are all covered. No secrets found committed.
  • GOOD Per-user Firestore scoping. The users/{userId} rules are correct and the header comment documents what catch-all they replaced. The playmat gap (F1) is an omission from this same good work, not an absence of thought.
  • GOOD Single-source versioning. __APP_VERSION__ is defined from package.json in vite.config.ts, so the release tag, manifest icons, and in-app version cannot drift.
  • GOOD Offline-first instincts. R2 and Pokémon CDN runtime caches are configured correctly; the QR generator is dependency-free and works offline. The precache misconfiguration (F2) is the one thing undermining an otherwise deliberate PWA design.

7. Explicitly NOT a Vulnerability

To save the next reviewer time: the Firebase apiKey hardcoded in src/utils/firebase.ts:14 is not a leaked secret. Firebase Web API keys are public identifiers by design; access control lives in Firestore rules. Please do not file this as a finding — the real rule-level issues are F1, F5 and F6 above.

Likewise, VITE_* variables are compile-time inlined and visible in the bundle by design; the issue in F4 is that a secret was placed in one, not that the mechanism is broken.
