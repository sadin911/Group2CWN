2. วิเคราะห์เจาะลึกข้อเสนอ P1–P6 (ข้อดี ข้อเสีย และข้อเสนอแนะ)

P1 ย้าย history ออกจาก Room Document

การวิเคราะห์ของ Claude: ถูกต้อง 100% การเก็บ 15 snapshot เต็มในรูทเอกสารทำให้ payload โตถึง ~600 KB ต่อ 1 write เฉียดเพดาน 1 MB ของ Firestore

👍 ข้อดี:
  • ลด Payload ที่อัปโหลด/ดาวน์โหลดทันที >90% (เหลือ ~35-40 KB)
  • ตัดความเสี่ยงเกมยาวแล้วชนเพดาน 1 MB ของ Firestore จนกระดานค้างเงียบ
  • ซิงก์ข้ามเครื่องเร็วขึ้นทันที ลด Latency ของเครือข่ายมือถือ
⚠️ ข้อจำกัด & จุดต้องระวัง:
  • ปัจจุบัน Mobile Controller มีปุ่ม Undo (handleUndo ใน PlaymatMobileController.tsx:915) ไม่ใช่มีแค่ Host
  • ถ้าเก็บ history ไว้ใน Host Memory เครื่องเดียว: มือถือของผู้เล่นจะกด Undo ไม่ได้ และถ้า Host บังเอิญรีเฟรชหน้าจอ ประวัติย้อนหลังจะหายไปทันที
💡 ข้อเสนอแนะแนวทางปฏิบัติ (Actionable Strategy):
  1. ระยะสั้น (Immediate Fix): ลด historyStack.length จาก 15 เหลือ 3 ชุด ทันที ซึ่งเพียงพอสำหรับการแก้มือ 1-2 สเต็ป แต่จะกดขนาด payload จาก 600 KB เหลือเพียง ~100 KB (ปลอดภัยจากเพดาน 1MB แน่นอน โดยไม่ต้องเปลี่ยนโครงสร้างโค้ด)
  2. ระยะกลาง (Complete Fix): แยก Subcollection playmat_rooms/{roomCode}/history/{seq} โดยใน doc หลักเก็บเฉพาะ historySeq: number เมื่อมีการกด Undo จึงค่อย query snapshot ล่าสุดกลับมา

P2 เขียนเฉพาะ Delta แทน setDoc ทั้งก้อน / ย้ายไป Realtime Database

👍 ข้อดี:
  • ลดปริมาณข้อมูลที่ส่งในแต่ละ action ลงเหลือไม่กี่ร้อยไบต์
  • Realtime Database มี WebSocket sync, latency ต่ำ (<50ms) และคิดเงินตาม bandwidth
⚠️ ข้อจำกัด & จุดต้องระวัง:
  • ข้อจำกัดของ Firestore กับ Array: การ์ดบนกระดาน เช่น p1.bench เป็น Array<PlaymatCard> ใน Firestore เราไม่สามารถใช้ dot notation อัปเดตสมาชิกเดี่ยวใน Array เช่น updateDoc(ref, { 'p1.bench[2].damageCounters': 30 }) ได้ หากจะอัปเดต ต้องส่งทั้ง Array ของ Bench อยู่ดี
  • การย้ายไป RTDB ถือเป็น Major Migration: ต้องเปิด Service ใหม่, เขียน Rules ใหม่, และเขียน Sync Engine ใหม่ทั้งหมด ซึ่งกระทบความเสถียรของแอปอย่างรุนแรง
💡 ข้อเสนอแนะแนวทางปฏิบัติ:

ยังไม่แนะนำให้ย้ายไป RTDB ในเวลานี้ แต่ให้ใช้เทคนิค Partitioned Update บน Firestore แทน: ใน PlaymatAction เราทราบอยู่แล้วว่า Action นั้นเป็นของ p1 หรือ p2 ดังนั้นแทนที่จะเขียนทั้งบอร์ด ให้เขียนเฉพาะ updateDoc(ref, { p1: nextState.p1, updatedAt: ... }) ซึ่งลด payload ลง 50% ทันทีโดยไม่ต้องแก้สถาปัตยกรรมระบบ

P3 เพิ่ม Wake Lock + Haptics — เห็นด้วย 100% (High Priority)

การวิเคราะห์: ตรงเป้าที่สุด การที่จอมือถือ/แท็บเล็ตดับระหว่างแข่ง TCG บนโต๊ะจริงคือปัญหาใหญ่ที่สุดของประสบการณ์ใช้งาน

👍 ข้อดี:
  • ใช้แรงน้อยมาก (~30 บรรทัดผ่าน custom hook useWakeLock)
  • จอเปิดค้างตลอดแมตช์ ปลดล็อกความลื่นไหลของการเล่นจริง
  • Haptics ช่วยให้ผู้เล่นรู้ว่าการแตะวางการ์ดสำเร็จ โดยไม่ต้องละสายตาจากการ์ดจริงบนโต๊ะ
⚠️ ข้อจำกัดทางเทคนิค:
  • iOS Safari ไม่รองรับ navigator.vibrate() (Apple ปิดกั้นไว้ใน WebKit) ต้องใส่ Feature Detection ป้องกัน runtime error
  • Wake Lock บน iOS Safari รองรับตั้งแต่เวอร์ชัน 16.4+
  • ต้อง handle event visibilitychange เพื่อ re-acquire lock เมื่อผู้ใช้สลับแอปกลับมา
💡 ข้อเสนอแนะแนวทางปฏิบัติ:

อนุมัติให้ดำเนินการเป็นอันดับแรกสุด สร้าง src/hooks/usePlaymatSensors.ts จัดการทั้ง Wake Lock และ Haptics ใน hook เดียว

P4 เปลี่ยน HTML5 Drag-and-Drop เป็น Pointer Events (ร่วมกับ P6)

การวิเคราะห์: จริงอย่างที่ Claude ชี้ — HTML5 Drag-and-Drop (`draggable`, `onDragStart`) ไม่ทำงานบน Touchscreen เบราว์เซอร์ส่วนใหญ่ไม่ยิง Drag Event เมื่อสัมผัสด้วยนิ้ว

👍 ข้อดี:
  • แท็บเล็ตและมือถือสามารถสัมผัสและลากการ์ดลงสนามได้จริงตาม Concept
  • Pointer Events รองรับ Touch, Mouse, Pen อย่างเสมอภาค
⚠️ ข้อจำกัด & จุดต้องระวัง:
  • การเขียน Pointer Events แบบ Vanilla (คำนวณ Drag Ghost, Collision Box, document.elementFromPoint) มีความซับซ้อนสูง และอาจเจอปัญหา Gesture ไปแย่งกับการเลื่อน Scroll ของถาดการ์ด
💡 ข้อเสนอแนะเชิงกลยุทธ์ (Strategic Synergy):

แทนที่จะเขียนดิบ Pointer Events เอง ให้นำ framer-motion (ซึ่งอยู่ใน package.json อยู่แล้ว) มาใช้ตามข้อเสนอ P6 ไปพร้อมกัน เพราะ <motion.div drag dragSnapToOrigin /> ของ Framer Motion:

  • รองรับ Pointer Events และ Touch หน้าจอสัมผัส 100% โดยอัตโนมัติ
  • มีฟิสิกส์การดีดกลับเข้าที่เดิมเมื่อปล่อยผิดตำแหน่ง (Snap-back physics)
  • แอนิเมชันลื่นไหล 60fps โดยไม่ต้องเขียนโค้ดจับพิกัดเองนับร้อยบรรทัด

P5 ยุบบอร์ด 3 ตัว (6,576 บรรทัด) & Reducer Unification

การวิเคราะห์: ความเห็นของ Claude เรื่องการมี Reducer applyPlaymatAction ที่ดีอยู่แล้วแต่ UI กลับไปกระจาย 75 useState เป็นการวิเคราะห์เชิงสถาปัตยกรรมที่ถูกต้อง

👍 ข้อดี:
  • ลดความซ้ำซ้อนของโค้ดอย่างมหาศาล (DRY)
  • ป้องกัน State Drift และบั๊ก stale-closure ระหว่าง DuelBoard และ MobileController
  • เขียน Unit Test ครอบคลุมได้ง่ายขึ้น
⚠️ ข้อจำกัด & ความเสี่ยงสูง (High Regression Risk):
  • ทั้ง 3 บอร์ดมี Layout แตกต่างกันอย่างสิ้นเชิง:
    • PlaymatHostBoard: จอใหญ่ แนวนอน แบ่ง 2 ฝั่งหันหน้าเข้าหากันสำหรับวางกลางโต๊ะ
    • PlaymatMobileController: จอมือถือแนวตั้ง ออกแบบให้เข้ากับ iPhone Safe-Area, มีชุด Quick Meta Chips, และ Touch Drawer
    • PlaymatDuelBoard: หน้าจอ Split-Screen สำหรับการเล่นออนไลน์ผ่านจอคอม/แท็บเล็ต
  • การ Rewrite รวดเดียว 6,500 บรรทัด มีโอกาสสูงมากที่จะทำลาย Responsiveness หรือกระทบ E2E Test ทั้ง 172 ตัว
💡 ข้อเสนอแนะแนวทางปฏิบัติ:

อย่า Rewrite แบบ Big-Bang! ให้แบ่งเป็น 3 Phase:

  • Phase 1 (Safe Extraction): ดึง Presentational Components ที่ไม่มี State ออกมาก่อน เช่น CardSprite, DamageCountersBadge, AttachedEnergyList
  • Phase 2 (Zone Modules): ดึง BenchRow, ActiveSpot, PrizeZone ที่ใช้ layout styling แยกตาม board type
  • Phase 3 (State Unification): เปลี่ยน State Management ภายในบอร์ดให้ Dispatch ผ่าน Reducer

3. สรุปตารางเปรียบเทียบและการจัดลำดับความสำคัญ (Roadmap)

ข้อเสนอผลตอบแทน (ROI)ความเสี่ยง (Risk)มติความเห็นลำดับดำเนินการ
P3: Wake Lock & Haptics สูงสุด (UX) ต่ำมาก เห็นชอบ 100% — ทำทันที Sprint 1 (ทันที)
P1: ย้าย/ลดขนาด History สูงมาก (Perf) ปานกลาง เห็นชอบแบบปรับปรุง — ลดเหลือ 3 snapshot ก่อน จากนั้นค่อยย้ายลง Subcollection Sprint 1 (ทันที)
P4 + P6: Motion Drag บน Touch สูง (Touch Support) ปานกลาง เห็นชอบ — แนะนำให้ใช้ Framer Motion Drag แทนการเขียน Pointer Event เอง Sprint 2
P2: Partitioned Update (Delta) ปานกลาง ปานกลาง เห็นชอบเฉพาะ Firestore Partition — ยังไม่แนะนำให้ย้ายไป Realtime Database Sprint 2
P5: Component & Reducer Refactoring ปานกลาง (Maintainability) สูงมาก (Regression) เห็นชอบแบบแบ่ง 3 เฟส — เริ่มจาก Dumb UI Components เพื่อรักษาความปลอดภัยของระบบ Sprint 3
