1. Blockers ค้างอยู่ (ต้องแก้ก่อน)

B1 rules ปัจจุบันจะ deny การสร้างห้องทุกครั้ง

// firestore.rules — เพิ่มมาในรอบที่แล้ว
allow create: if request.resource.data.keys().hasAll(['roomCode', 'mode'])
              && request.resource.data.roomCode == roomCode;
$ grep -n "mode" src/types/playmat.ts
(ไม่เจอ)

PlaymatRoomState ไม่มี field mode เลย hasAll จึงเป็น false เสมอ และ setDoc บน doc ที่ยังไม่มีอยู่ = create ในสายตา rules → ถูก deny ทุกครั้ง

อาการจะไม่โผล่ตอน dev เพราะ createPlaymatRoom() (playmatSyncService.ts:693-702) ใช้ Promise.race timeout 2 วิ + catch ที่แค่ console.warn และห้องยังอยู่ใน memoryRooms + BroadcastChannel → จอ host ทำงานปกติ แต่มือถือคนละเครื่องจะไม่เห็นห้องเลย

ทำ: เพิ่ม mode: 'solo' | 'duel' | 'host' เข้า PlaymatRoomState และ set ใน createInitialRoomState() (:33-54) — ทางนี้ดีกว่าเพราะทำให้ rule มีความหมายจริง และ P5 ก็ต้องใช้ field นี้อยู่แล้ว (ทางเลือกที่เร็วกว่า: ลบ 'mode' ออกจาก hasAll)
เกณฑ์ผ่าน: emulator test ยืนยันว่า createPlaymatRoom() เขียนสำเร็จ (ดู §4)

B2 ห้อง Playmat ยังเขียนทับได้จากทุกคนแบบไม่ต้องล็อกอิน

allow read:   if true;
allow update: if request.resource.data.roomCode == roomCode;

เช็คแค่ว่า field roomCode ยังตรงกับ document ID — ซึ่งไม่มี client ไหนเปลี่ยนค่านี้ และ setDoc(..., {merge:true}) ก็พก field นี้ไปด้วยเสมอ → เงื่อนไขเป็นจริงทุกกรณี เท่ากับ allow write: if true เดิม room code สั้นและเดาได้ ใครก็แก้ HP / prize / isTerminated ของห้องคนอื่นได้

ทำ: ใช้ Firebase anonymous auth — ได้ request.auth.uid จริงโดยไม่ต้องบังคับ Google sign-in ซึ่งตรงกับเจตนาเดิมที่อยากให้มือถือ guest เข้าได้ จากนั้นเก็บ hostUid + participants[] ตอน create แล้ว gate update ด้วย request.auth.uid in resource.data.participants และห้ามแก้ roomCode / pin / createdAt ผ่าน affectedKeys()

                        + discard ~25 + lostZone ~5  ≈ 55 ใบ  ≈ 20 KB

เกมยาวๆ จะชนเพดาน 1 MiB แล้วเขียนไม่ได้อีกเลย โดย error ถูก console.warn กลืน ผู้เล่นจะเห็นกระดาน "ค้าง" โดยไม่มีข้อความอะไรบอก

ทำ: undo ไม่จำเป็นต้อง sync ข้ามเครื่อง — เก็บ history ไว้ใน memoryRooms ฝั่ง host เท่านั้น (ทางที่ง่ายและถูกที่สุด) หรือถ้าต้องการให้ข้ามเครื่องจริงๆ ให้ย้ายไป subcollection playmat_rooms/{code}/history/{seq} แล้วเก็บแค่ historyDepth: number ไว้ใน doc หลัก
สำคัญ: applyPlaymatAction เป็น pure reducer อยู่แล้วและมี test 540 บรรทัด — แก้ตรงนี้แล้วรัน npm test จะเห็นทันทีว่า UNDO ยังทำงานไหม
เกณฑ์ผ่าน: ขนาด payload ต่อ action ลดลง ≥90% · playmatSyncService.test.ts ผ่านครบ 232 tests · UNDO ยังใช้ได้บนเครื่อง host

P2 เขียนเฉพาะ delta แทน setDoc ทั้งก้อน

แม้ตัด history ออกแล้ว ทุก action ยังส่ง board ทั้งกระดาน (~40 KB) ทั้งที่การวางแดเมจเปลี่ยนแค่ตัวเลขเดียว Firestore คิดเงินต่อ document write และ latency ผูกกับขนาด payload

ทำ: ใช้ updateDoc() กับ field path เจาะจง เช่น updateDoc(ref, { 'p1.active.damageCounters': 30, updatedAt: ... }) โดย map จาก PlaymatActionType → field path ที่ action นั้นแตะจริง
ทางเลือกที่ดีกว่าถ้ายอมเปลี่ยน transport: Firebase Realtime Database เหมาะกับงานนี้มากกว่า Firestore — คิดเงินตาม bandwidth ไม่ใช่ต่อ write, เขียนแบบ path-level ได้โดยธรรมชาติ (rooms/ABC/p1/active/damageCounters) และมี onDisconnect() ให้ทำ presence ฟรี ส่วน Firestore เด่นเรื่อง query ซับซ้อน ซึ่ง playmat ไม่ใช้เลย — เป็นข้อเสนอ ไม่ใช่ข้อบังคับ ถ้าเลือกทางนี้ควรคุยกับเจ้าของโปรเจกต์ก่อน

P4 เปลี่ยน HTML5 drag-and-drop เป็น Pointer Events

HTML5 drag-and-drop ไม่ยิง event บนจอสัมผัสเลย — แต่คอนเซปต์ของฟีเจอร์คือ "แท็บเล็ตเป็นกระดาน" ซึ่งเป็นอุปกรณ์ touch ล้วน แปลว่าบอร์ดหลักลากการ์ดไม่ได้บนอุปกรณ์เป้าหมายของตัวเอง แล้วยังมีระบบ input สองแบบที่ไม่ตรงกันระหว่างสองไฟล์

ทำ: รวมเป็น Pointer Events ทั้งระบบ (onPointerDown/Move/Up + setPointerCapture) ซึ่งครอบคลุมทั้ง mouse / touch / stylus ในโค้ดชุดเดียว แล้วเอา logic นี้ไปไว้ในฮุกกลางที่ทั้งสามบอร์ดใช้ร่วมกัน (ต่อยอด src/hooks/useDragSwap.ts ที่มีอยู่แล้วแต่ playmat ไม่ได้ใช้)
เพิ่ม touch-action: none บนโซนที่ลากได้ ไม่งั้น browser จะแย่ง gesture ไปทำ scroll
เกณฑ์ผ่าน: E2E ใน project [mobile] ลากการ์ดจากมือขึ้น active ได้จริง (ตอนนี้ยังไม่มีเทสต์ที่ครอบคลุมการลาก)

4. ข้อควรระวังเรื่องการตรวจสอบ — สำคัญมากสำหรับงานชุดนี้

Quality gate ทั้ง 4 ตัวของโปรเจกต์นี้ไม่ครอบคลุม firestore.rules เลย รอบที่แล้ว lint / build / vitest / playwright ผ่านหมด ทั้งที่ rule ตัวใหม่จะทำให้สร้างห้องไม่ได้ใน production

สาเหตุอยู่ใน log ของ Playwright เอง:

[console.warn] Firestore fetchPlaymatAllowedUsers skipped/failed: FirebaseError: Missing or insufficient permissions.
[console.error] @firebase/firestore: Could not reach Cloud Firestore backend.
              The client will operate in offline mode until it is able to successfully connect.

E2E รันโดยที่ Firestore ต่อไม่ได้ แล้วแอปก็ catch แล้ว fallback ไป memoryRooms + BroadcastChannel ทุกอย่างเลยเขียว โดยไม่ได้พิสูจน์อะไรเกี่ยวกับ rules เลยแม้แต่นิดเดียว

ดังนั้นสำหรับงานชุดนี้ ขอให้เพิ่ม emulator test ด้วย — firebase.json ตอนนี้มีแค่ firestore.rules + indexes ยังไม่มี block emulators เลย:

npm i -D @firebase/rules-unit-testing

เคสที่ต้องมีอย่างน้อย 4 ข้อ:

  • สร้างห้องสำเร็จ — เคสนี้จะจับ B1 ได้ทันที
  • คนที่ไม่ได้อยู่ในห้อง แก้ห้องคนอื่นไม่ได้ (B2)
  • non-admin แก้ market_prices.regular ไม่ได้
  • viewCount เพิ่มได้ทีละ 1 เท่านั้น

นี่คือสิ่งที่ทำให้ round นี้ต่างจาก round ที่แล้ว: ถ้าไม่มี test ตัวนี้ เราจะไม่มีทางรู้ว่า rules ที่แก้ไปถูกหรือผิด จนกว่าจะมีผู้เล่นจริงเจอปัญหา
