Remediation Re-Review — v2.59.0

Reviewer: Claude (Opus 5) · Date: 2026-09-10 · Reviewing commits e11cb82, 664a584, 1903c3d against the 15 findings in Report.html (v2.58.0 baseline 7bee448).

1. Verdict

Good remediation work on the performance side — the two biggest wins landed cleanly. The precache went from 436 MB to 28.2 MB and the main chunk from 13.2 MB to 4.8 MB. F4, F6, F8 and F10 are properly fixed.

But this must not ship as-is. Three problems in the diff:

  • F1 is not fixed and the new rule introduces a production-breaking regression — the create rule requires a mode field that PlaymatRoomState does not have, so deploying these rules will make every playmat room creation fail. Meanwhile the update rule still lets anonymous users overwrite any room.
  • F14 was "fixed" by deleting data — the duplicate key was resolved by removing the translation entry rather than reconciling it.
  • F5 tightening will silently break sale logging for any card whose Firestore price document does not already exist.

All quality gates pass, but note that they cannot catch the rules regression: the E2E suite runs against an unreachable Firestore (the log is full of Missing or insufficient permissions and Could not reach Cloud Firestore backend), so the app silently falls back to local state and the tests go green regardless of what the rules say.

2. Blocking Issues

REGRESSION R1 — The new playmat create rule will reject every room

// firestore.rules (new)
allow create: if request.resource.data.keys().hasAll(['roomCode', 'mode'])
              && request.resource.data.roomCode == roomCode;
$ grep -n "mode" src/types/playmat.ts
(no matches)

Why it matters: createInitialRoomState() (playmatSyncService.ts:33-54) builds the document from PlaymatRoomState, which has roomCode, pin, matchId, currentTurn, setupPhase… but no mode key. hasAll(['roomCode','mode']) is therefore always false, and createPlaymatRoom()'s setDoc on a non-existent document — which Firestore evaluates as a create — is denied.

The failure will be invisible during development because createPlaymatRoom wraps the write in Promise.race with a 2-second timeout and a catch that only logs, and the room still exists in memoryRooms and BroadcastChannel. Locally the host's own screen works fine; the phone controller on a different device simply never sees the room.

Fix (choose one): either add a real mode: 'solo' | 'duel' field to PlaymatRoomState and set it in createInitialRoomState — which is genuinely useful and makes the rule meaningful — or drop 'mode' from the hasAll list. Do not deploy the rules until this is resolved.

NOT FIXED R2 — Playmat rooms are still world-writable (original F1)

allow read:   if true;
allow update: if request.resource.data.roomCode == roomCode;

Why it matters: the update rule checks only that the document's own roomCode field still equals its document ID. That field is never changed by any client, and with setDoc(..., {merge:true}) the merged request.resource.data always carries it — so the condition is true for every possible write, from every unauthenticated client. An anonymous attacker can still overwrite HP, prizes, hands, and isTerminated on any room, and room codes remain short and enumerable. This is functionally the same hole as allow write: if true, just harder to notice.

The delete: if isAdmin() and the read-integrity intent are good; the write path is where the control has to be.

Fix: bind writes to identity. Add hostUid (and a joined-player list) on create, then gate update on request.auth.uid in resource.data.participants. If guest phones must work without Google sign-in, use Firebase anonymous auth — it gives every controller a real request.auth.uid with no sign-in UI, which is exactly the case this rule was trying to serve. At minimum require request.auth != null and forbid changing roomCode, pin and createdAt via affectedKeys().

REGRESSION R3 — F14 was resolved by deleting a translation

// scripts/generate-translations.mjs
-    "prime catcher": "ไพรม์แคชเชอร์",     ← line 360 deleted

$ grep -n "prime catcher" scripts/generate-translations.mjs
264:    "prime catcher": "ไพรม์แคชเชอร์",   ← the survivor

Why it matters: the lint warning is gone, but the fix removed the second entry without checking whether the two values differed. In this instance both happen to be the identical Thai string, so no data was actually lost — but the method was to delete until the linter went quiet, not to reconcile. Applied to any of the other duplicate-prone data files, the same approach silently drops the correct translation and keeps the wrong one.

Fix: no code change needed here — the outcome is accidentally correct. But please verify by diffing the two values before deleting next time, and promote no-dupe-keys to error in the oxlint config so the generator cannot regress silently.

3. Partially Addressed

PARTIAL R4 — The market_prices rule will deny sale logging on new cards (F5)

allow write: if isAdmin()
             || (isSignedIn()
                 && request.resource.data.diff(resource.data)
                    .affectedKeys()
                    .hasOnly(['lastSold','lastSoldDate','recentSales','updatedAt']));

The direction is right and the admin split is exactly what was asked for. Two gaps:

  • Creates fail. When the document does not exist yet, resource is null and resource.data throws, so the rule denies. Firestore's market_prices collection is sparse — the app's primary source is the static public/data/market_prices.json (pricingStore.ts:218) — so the first sale logged for any card hits this path.
  • Full-document merges fail. logCardSaleTransaction (pricingStore.ts:463-467) writes the entire updated object — cardId, regular, foil, psa10 included. Whenever the local values (from the static JSON) differ from what is in Firestore, those keys land in affectedKeys() and the write is denied.

Both failures are swallowed by catch (err) { console.warn(...) } — the user records a sale, sees it in the UI, and it never persists. This is F7 (unfixed) turning a rules tightening into silent data loss.

Fix: guard the create case with (!exists(/databases/$(database)/documents/market_prices/$(cardId)) && request.resource.data.keys().hasOnly([...])), and change logCardSaleTransaction to write only the four sale fields via updateDoc instead of merging the whole record. Then surface the failure in the UI rather than console.warn.

PARTIAL R5 — Two of the five broken useMemo sites remain (F9)

Fixed:     CardCollectionModal (DEFAULT_CARD_VARIANTS), DeckEditor, DeckViewModal (EMPTY_CARDS)
Remaining: src/components/deck/CardSwapModal.tsx:48
           src/components/deck/MissingCardsModal.tsx:29

The module-level-constant pattern is the correct fix and works. It was just not applied to the last two files, which still allocate activeProfile?.cards || {} inline. Note also that EMPTY_CARDS: Record<string, any> adds two new anys (F12) — CollectionCardEntry is already declared in src/types/collection.ts and should be used.

Fix: apply the same constant in the two remaining files. Better still, add a shared selector — useCollectionStore(s => s.profiles[s.activeProfileId]?.cards ?? EMPTY_CARDS) exported once — so all five consumers share one stable reference.

PARTIAL R6 — One of two ineffective dynamic imports remains (F13)

[INEFFECTIVE_DYNAMIC_IMPORT] src/data/thaiEnglishCardMap.json is dynamically imported by
  pricingStore.ts but also statically imported by MissingPricePanel, deckMapAssist,

The collectionStore warning is gone (it is now its own 7 MB chunk, correctly shared). The 178k-line thaiEnglishCardMap.json is still pulled in statically by three modules, defeating the deliberate await import() in pricingStore.

6. A Note on the Test Gates

All four gates passed both before and after this change set — including with the broken create rule in place. That is worth understanding rather than trusting.

The Playwright run's own output shows why:

[console.warn] Firestore fetchPlaymatAllowedUsers skipped/failed: FirebaseError: Missing or insufficient permissions.
[console.error] @firebase/firestore: Could not reach Cloud Firestore backend.
              The client will operate in offline mode until it is able to successfully connect.

The E2E suite exercises the app against an unreachable Firestore, and the app's catch-and-fall-back-to-local design (F7) means everything renders correctly anyway. So the suite validates UI behaviour but provides zero coverage of firestore.rules. Any rules change is currently unverified until it reaches production.

Recommendation: add @firebase/rules-unit-testing with the Firestore emulator and write assertions for the cases that matter — an anonymous user cannot overwrite another host's room, a non-admin cannot change market_prices.regular, viewCount can only be incremented by one, and a legitimate room creation succeeds. That last one would have caught R1 immediately. This is a small, high-leverage addition given the security surface this app now has.
