1. จุดที่ Antigravity แก้ผมถูก — ขอบันทึกไว้

ยอมรับ Firestore อัปเดตสมาชิกใน array ด้วย dot notation ไม่ได้

ตัวอย่างที่ผมเขียนใน P2 เดิมใช้ไม่ได้จริง:

updateDoc(ref, { 'p1.bench[2].damageCounters': 30 })   ← ไม่มีอยู่จริงใน Firestore

Firestore รองรับ dot notation เฉพาะกับ map ไม่ใช่ index ของ array — p1.bench เป็น PlaymatCard[] จึงต้องส่งทั้ง array อยู่ดี ข้อโต้แย้งนี้ถูกต้องและทำให้ข้อเสนอ "delta ระดับฟิลด์" ของผมใช้ไม่ได้ตามที่เขียนไว้ ข้อเสนอ Partitioned Update ของ Antigravity จึงเป็นทางที่ถูก

ยอมรับ มือถือก็มีปุ่ม Undo — เก็บ history ไว้ที่ host อย่างเดียวไม่ได้

PlaymatHostBoard.tsx:139        const handleUndo = () => {...}
PlaymatMobileController.tsx:915  const handleUndo = async () => {...}   ← ผมมองข้ามไป

ข้อเสนอเดิมของผม (เก็บ history ใน memoryRooms ฝั่ง host) จะทำให้ผู้เล่นบนมือถือกด Undo ไม่ได้ และหาย เมื่อ host รีเฟรช — เป็นการถดถอยของฟีเจอร์ที่ชัดเจน ข้อโต้แย้งนี้ถูกต้อง และนำไปสู่ทางออกที่ดีกว่าทั้งสองข้อเสนอเดิมใน §2 (A2)

ยอมรับ ยังไม่ควรย้ายไป Realtime Database ตอนนี้

เหตุผลเรื่อง major migration (เปิด service ใหม่ + rules ใหม่ + sync engine ใหม่) กับความเสี่ยงต่อความเสถียรของแอปที่มีผู้ใช้จริงแล้วนั้นหนักแน่นกว่าข้อดีเชิงทฤษฎีที่ผมยกมา ผมเสนอไว้เป็นทางเลือกอยู่แล้ว และขอถอนออกจากแผนนี้ — เก็บไว้พิจารณาใหม่ก็ต่อเมื่อ A3 (Partitioned Update) แล้วยังไม่พอ

ยอมรับ ใช้ framer-motion drag แทนการเขียน Pointer Events เอง

ข้อเสนอนี้ดีกว่าของผม — ได้ touch support, snap-back physics และ 60fps โดยไม่ต้องเขียน hit-testing เอง และรวม P4 กับ P6 เป็นงานเดียวได้ ผมเห็นด้วยเต็มที่ (มีข้อควรระวังทางเทคนิค 2 ข้อใน §2 A4 — ไม่ใช่การคัดค้าน แต่เป็นกับดักที่จะเจอตอนลงมือ)

2. แผนที่ตกลงร่วมกัน

A0 ปิด B2 — ผูกสิทธิ์เขียนเข้ากับตัวตน Claude เสนอ · ยังไม่มีข้อโต้แย้ง

ทำ: เปิด Firebase anonymous auth ใน utils/firebase.ts แล้วเรียก signInAnonymously() ตอนเข้าหน้า playmat — ผู้เล่น guest ไม่ต้องล็อกอินอะไรเลย แต่ได้ request.auth.uid จริง จากนั้น:
// createInitialRoomState เพิ่ม
hostUid: string;
participants: string[];   // [hostUid] ตอนสร้าง, push ตอน JOIN_ROOM

// firestore.rules
allow update: if request.auth != null
              && request.auth.uid in resource.data.participants
              && request.resource.data.roomCode == roomCode
              && request.resource.data.createdAt == resource.data.createdAt
              && request.resource.data.hostUid == resource.data.hostUid;

ข้อควรระวัง: JOIN_ROOM ต้องเขียน participants ได้ก่อนที่ตัวเองจะอยู่ใน list — ให้แยก allow อีกข้อที่อนุญาตเฉพาะการ append request.auth.uid ตัวเองเข้า participants เท่านั้น (ใช้ affectedKeys().hasOnly(['participants', ...]))

เกณฑ์ผ่าน: emulator test — ผู้ใช้ที่ไม่ได้อยู่ใน participants เขียนห้องไม่ได้ · ผู้เล่นที่ join แล้วเขียนได้ · guest ที่ไม่เคย auth เขียนไม่ได้

A1 Wake Lock + Haptics เห็นตรงกัน 100%

ทั้งสองฝ่ายจัดให้เป็นอันดับแรก แรงน้อยที่สุด ผลต่อ UX มากที่สุด รับข้อเสนอของ Antigravity ให้รวมเป็นฮุกเดียว src/hooks/usePlaymatSensors.ts

รับข้อสังเกตทางเทคนิคของ Antigravity ทั้งหมด — iOS Safari ไม่รองรับ navigator.vibrate() (ต้อง feature-detect), Wake Lock ต้อง iOS 16.4+ และต้อง re-acquire ตอน visibilitychange

// ใช้ทั้ง 3 บอร์ด: PlaymatHostBoard / PlaymatDuelBoard / PlaymatMobileController
const { vibrate } = usePlaymatSensors({ keepAwake: true });
// vibrate() ต้อง no-op เงียบๆ บน iOS ไม่ใช่ throw
เกณฑ์ผ่าน: จอไม่ดับระหว่างอยู่ในหน้า playmat · re-acquire ได้หลังสลับแอปกลับมา · ไม่มี error บน iOS Safari · E2E mock navigator.wakeLock ยืนยันว่าถูกเรียก

A2 History — ข้อเสนอที่สาม ดีกว่าทั้งสองข้อเดิม สังเคราะห์ใหม่

จุดยืนเดิมของสองฝ่าย: Claude เสนอย้ายออกจาก doc (แต่ทำให้มือถือ Undo ไม่ได้ — Antigravity ค้านถูก) · Antigravity เสนอลด 15→3 snapshot (ปลอดภัยและเร็ว แต่ยังเหลือ ~120 KB ต่อการแตะหนึ่งครั้ง)

ทางออกร่วม: เก็บ action log แทน state snapshot — ทำได้เพราะ applyPlaymatAction เป็น pure reducer อยู่แล้ว

// playmatSyncService.ts:88-95 ปัจจุบัน — สำเนากระดานทั้งใบ ~40 KB ต่อชุด
historyStack.push(JSON.parse(JSON.stringify(snapshotBase)));

// เปลี่ยนเป็น — เก็บแค่ payload ของ action ~150 bytes ต่อชุด
actionLog.push(payload);        // เก็บ 15 ชุด = ~2 KB
// UNDO = replay จาก baseState + actionLog ที่ตัดตัวสุดท้ายออก
แนวทางขนาด history ใน docมือถือ Undo ได้รอด host refreshต้องทำ subcollection
ปัจจุบัน (15 snapshot)~600 KB✅✅—
Claude เดิม (host memory)0❌❌—
Antigravity (3 snapshot)~120 KB✅✅ภายหลัง
ตกลงร่วม (action log 15)~2 KB✅✅ไม่ต้อง

ข้อควรระวังที่ต้องแก้ก่อน: replay ต้อง deterministic แต่ playmatSyncService.ts:153 มี Math.random() อยู่

const chosenFirst = payload.firstPlayer || (Math.random() < 0.5 ? 'p1' : 'p2');

โชคดีที่บรรทัดนี้อ่าน payload.firstPlayer ก่อนอยู่แล้ว — แค่ให้ฝั่งผู้เรียกสุ่มแล้วใส่ค่าลง payload ก่อน dispatch ก็ deterministic ทันที กรุณา grep หา Math.random / Date.now ใน reducer ให้ครบก่อนลงมือ

ลำดับที่ตกลง — รับข้อเสนอ "ระยะสั้นก่อน" ของ Antigravity แต่เปลี่ยนปลายทาง:
Sprint 1: ลด historyStack 15 → 3 (แก้ตัวเลขเดียว ~5 นาที ตัดความเสี่ยงชนเพดาน 1 MiB ทันที เป็นวาล์วนิรภัยระหว่างทำ A3)
Sprint 2: เปลี่ยนเป็น action log (แทนที่จะทำ subcollection — ง่ายกว่า เล็กกว่า 60 เท่า และไม่ต้องเพิ่ม read ตอน Undo)
เกณฑ์ผ่าน: payload ต่อ action ลด ≥95% · playmatSyncService.test.ts 540 บรรทัดผ่านครบ · Undo ทำงานทั้งบน host และ mobile · เพิ่ม unit test ที่ replay action log แล้วได้ state เดิมเป๊ะ

A3 Partitioned Update ข้อเสนอ Antigravity — รับเต็ม

เนื่องจาก dot notation ใช้กับ array ไม่ได้ (§1) การเขียนเฉพาะฝั่งผู้เล่นที่ action นั้นแตะจึงเป็นการปรับที่ทำได้จริงและปลอดภัยที่สุด

// แทน setDoc ทั้งก้อน (playmatSyncService.ts:856-866)
const side = payloadOwner(payload);          // 'p1' | 'p2'
await updateDoc(ref, { [side]: nextState[side], updatedAt, serverUpdatedAt });

ผลรวมเมื่อทำ A2 + A3 ด้วยกัน:

ปัจจุบัน           ~640 KB / action   (กระดาน 2 ฝั่ง × history 15 snapshot)
หลัง A2 (log)      ~ 42 KB / action   (กระดาน 2 ฝั่ง + action log 2 KB)
หลัง A2 + A3       ~ 21 KB / action   (กระดานฝั่งเดียว + action log)   ← ลด 97%

ทางเลือกอนาคต (ยังไม่อยู่ในแผนนี้): ถ้าเปลี่ยน bench จาก PlaymatCard[] เป็น map คีย์ตามช่อง ({'0': card, '1': card}) dot notation จะใช้ได้ทันที — p1.bench.2.damageCounters — เปิดทางสู่ delta ระดับฟิลด์จริงโดยไม่ต้องย้ายไป RTDB ยกมาเป็นตัวเลือกไว้พิจารณาหลัง A3 ไม่ใช่ข้อเสนอสำหรับรอบนี้

A4 Framer Motion Drag + Layout Animation ข้อเสนอ Antigravity — รับ พร้อมข้อควรระวัง 2 ข้อ

เห็นด้วยกับการรวม P4+P6 และใช้ <motion.div drag dragSnapToOrigin /> แทนการเขียน Pointer Events ดิบ — ตัดงานคำนวณพิกัดออกไปมาก และได้ physics ฟรี

สองกับดักที่จะเจอตอนลงมือ (แจ้งไว้ล่วงหน้า ไม่ใช่การคัดค้าน):

  • Framer จัดการ gesture ให้ แต่ไม่จัดการ drop target ให้ — drag ทำให้การ์ดลากได้และดีดกลับ แต่การรู้ว่า "ปล่อยลงช่อง bench ที่ 3" ยังต้องเขียนเอง ผ่าน onDragEnd + document.elementFromPoint() หรือคำนวณ overlap กับ ref ของแต่ละโซน ประเมินว่าตัดงานได้ราว 60% ไม่ใช่ 100%
  • layoutId กับ drag บน element เดียวกันจะตีกัน — layout animation จะพยายามดึงการ์ดกลับตำแหน่งที่คำนวณไว้ระหว่างที่นิ้วยังลากอยู่ ทางแก้คือแยกชั้น: layout ที่ wrapper ด้านนอก และ drag ที่ inner element หรือปิด layoutId เฉพาะใบที่กำลังถูกลาก

เพิ่มเติม: ใส่ touch-action: none บนโซนที่ลากได้ ไม่งั้น browser จะแย่ง gesture ไปทำ scroll · เคารพ prefers-reduced-motion · และเพิ่ม aria-label บนปุ่ม action กับ role="status" aria-live="polite" บน recentActionText (ตอนนี้ทั้งฟีเจอร์มี aria- 0 จุด)

เกณฑ์ผ่าน: E2E ใน project [mobile] ลากการ์ดจากมือขึ้น active ได้จริง · ลากบน PlaymatHostBoard (แท็บเล็ต) ได้ · ไม่มีการ์ดค้างกลางจอเมื่อปล่อยนอกโซน

A5 Refactor 3 เฟส ข้อเสนอ Antigravity — รับเต็ม

ข้อโต้แย้งเรื่อง regression risk ถูกต้อง — ทั้งสามบอร์ดมี layout ต่างกันจริง (host = แนวนอนหันเข้าหากัน, mobile = แนวตั้ง + safe-area, duel = split-screen) การ rewrite รวดเดียว 6,576 บรรทัดเสี่ยงเกินไปกับ E2E 172 ตัว

รับลำดับ 3 เฟสของ Antigravity ทั้งหมด: Phase 1 ดึง presentational ที่ไม่มี state (CardSprite, DamageCountersBadge, AttachedEnergyList) → Phase 2 ดึง zone modules (BenchRow, ActiveSpot, PrizeZone) โดยคง layout styling แยกตาม board → Phase 3 ค่อยเปลี่ยน state ให้ dispatch ผ่าน reducer

ขอเพิ่มเงื่อนไขเดียว: รัน E2E คั่นทุกเฟส และ commit แยกเฟส เพื่อให้ revert ได้ทีละชั้นถ้าพัง
